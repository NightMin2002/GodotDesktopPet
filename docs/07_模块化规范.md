# 模块化规范

> 本文档定义项目中代码拆分与重构的标准做法。新增功能或重构旧代码时，按本文档执行。

---

## 一、核心原则

1. **务实拆分，不极端化** — 只拆逻辑复杂、职责清晰的模块。3 行配置代码不值得单开文件。
2. **平坦胜于嵌套** — 同层级文件优于多层目录。`ui/context_menu/sec_pet.gd` 优于 `ui/context_menu/sections/pet/builder.gd`。
3. **保持可读性** — 每个文件控制在 100~400 行。超过 500 行考虑拆分，低于 50 行考虑合并。
4. **代码位置即文档** — 文件名和目录结构应能自解释职责，不需要额外索引。

---

## 二、已采用的模式

### 2.1 委托模式 (Delegation Pattern)

**适用场景**: 一个主控制器文件过大，包含多个并列的业务分区。

**做法**: 主控制器只保留协调逻辑（初始化、生命周期、通用工具），每个业务分区的构建+回调提取到独立的 builder 类。

**实际案例**: `context_menu.gd` → 5 个 `sec_*.gd`

```
# 主控制器 (context_menu.gd, 440行)
# 职责: 初始化、菜单开关动画、弹性追踪、持久化加载、通用工具函数
# 不做: 具体分区的 UI 构建、按钮回调、状态刷新

var _sec_pet: SecPet       # ← 委托对象
var _sec_behavior: SecBehavior

func _ready():
    _sec_pet = SecPet.new(self)     # 传入自身引用
    _sec_pet.build()                # builder 自行构建 UI

# Builder (sec_pet.gd, 325行)
extends RefCounted
var ctx  # 主控制器引用

func _init(context_menu) -> void:
    ctx = context_menu

func build() -> void:
    # 通过 ctx 访问主控制器的通用方法
    var btn = ctx._make_menu_btn("碎碎念", Color(...))
    ctx._bind_l3_trigger(btn, "chatter", "sec_pet")
```

**关键约定**:
- Builder 类继承 `RefCounted`，通过 `ctx` 访问主控制器
- 主控制器提供通用工具函数（`_make_menu_btn`, `_apply_capsule_style` 等）
- Builder 负责 UI 构建 + 回调 + 状态刷新
- 文件命名: `sec_<分区名>.gd`

### 2.2 模板方法模式 (Template Method Pattern)

**适用场景**: 多个子类有相同的流程骨架，仅细节（话术、参数、额外清理）不同。

**做法**: 基类实现完整流程，通过 hook 方法让子类注入差异点。

**实际案例**: `base_game.gd` 的关闭清理和自玩启动

```
# 基类 — 模板方法 (不需要子类覆写)
func _on_close_cleanup() -> bool:
    if not _game_over:
        _game_over = true
        _on_close_extra_cleanup()  # ← hook: 子类额外清理
        _losses += 1
        _save_scores()
        game_finished.emit(Result.LOSE)
        # 话术通过 hook 获取
        if was_auto:
            _pet.show_local_bubble(get_auto_close_lines()[...])
        else:
            _pet.show_local_bubble(get_close_speech_pool()[...])
    return true

# 子类 — 只提供数据，不重写流程
func _on_close_extra_cleanup() -> void:   # hook
    _tick_timer.stop()

func get_close_speech_pool() -> Array:    # hook
    return ["...中途退出？数据已保存。"]

func get_auto_close_lines() -> Array:     # hook
    return ["...训练中断。数据已归档。"]
```

**关键约定**:
- 模板方法本身子类**不覆写**
- Hook 方法以 `get_*` (数据) 或 `_on_*` (行为) 命名
- 基类提供合理默认值，子类按需覆写

### 2.3 工厂方法 (Factory Method)

**适用场景**: 多处代码重复创建相同结构的 UI 组件。

**做法**: 提取到基类的工厂方法，统一样式和结构。

**实际案例**: `base_game.gd` 的 UI 工厂

| 工厂方法 | 消除的重复 |
|----------|-----------|
| `_create_panel_skeleton(min_width, margins)` | 5 个游戏的面板骨架 |
| `_create_compare_row(parent, text)` | 5 个游戏的对比行 |
| `_create_score_rich_label()` | 4 个游戏的战绩标签 |
| `_create_game_panel_bg()` | 5 个游戏的面板背景 |

### 2.4 通用内嵌类 (Shared Inner Class)

**适用场景**: 多个子类定义了结构完全相同的内嵌类。

**做法**: 提取到基类作为公开内嵌类。

**实际案例**: `BaseGame.GridRenderer`

```
# 基类定义
class GridRenderer extends Control:
    var game
    func _ready(): focus_mode = FOCUS_ALL; grab_focus()
    func _draw(): if game: game._render(self)
    func _gui_input(event): if game: game._on_grid_input(event)
    func _process(delta): if game: game._grid_process(delta)

# 子类使用
_grid_renderer = GridRenderer.new()
_grid_renderer.game = self
```

## 三、模块化检查清单

重构前对照此清单决策：

| 检查项 | 判断标准 | 动作 |
|--------|---------|------|
| 文件超过 500 行？ | 是，且含多个并列分区 | 委托模式拆分 |
| 多个子类有相同流程？ | 仅话术/参数不同 | 模板方法提取 |
| 多处创建相同 UI？ | 3 处以上重复 | 工厂方法提取 |
| 多个文件定义相同内嵌类？ | 2 处以上完全相同 | 提取到基类 |
| 文件不足 50 行？ | 逻辑简单，无独立性 | 合并回主文件 |
| 目录超过 3 层？ | 层级过深 | 扁平化 |

## 四、命名规范

| 类型 | 命名规则 | 示例 |
|------|---------|------|
| 分区 builder | `sec_<分区名>.gd` | `sec_pet.gd`, `sec_behavior.gd` |
| 子系统委托 | `<职责>.gd` | `submenu_system.gd`, `info_sidebar.gd` |
| 游戏脚本 | `game.gd` (在各自目录下) | `games/snake/game.gd` |
| 通用基类 | `base_<类别>.gd` | `base_game.gd` |
| 状态机状态 | `<状态名>.gd` | `idle.gd`, `drag.gd` |

## 五、期望与红线

### 期望

- 每个文件打开后，5 秒内能理解它的职责
- 修改某个分区时，只需要打开 1~2 个文件
- 新增功能时，能直接复制现有 builder 作为模板
- 代码整齐干净，但不追求极端的解耦

### 红线

- **不要为了拆分而拆分** — 10 行代码不需要独立文件
- **不要引入抽象层** — 不用接口、不用依赖注入框架、不用注册表模式（除非已有先例）
- **不要破坏 Godot 惯例** — RefCounted 委托可以，但不要搞自定义模块加载器
- **不要嵌套超过 3 层目录** — `ui/context_menu/sec_pet.gd` 是上限
- **不要在 builder 之间互相引用** — 所有通信通过主控制器或 EventBus
