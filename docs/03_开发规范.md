# 🏗️ 开发规范与避坑指南

> 如何保持代码整洁、避免"巨大单文件噩梦"、以及 Godot 特有的坑。

---

## 1. 文件大小红线

| 规则 | 阈值 | 处理方式 |
|------|------|---------|
| 单个 `.gd` 文件 | **不超过 1000 行** | 超了就拆分 |
| 单个函数 | **不超过 50 行** | 超了就提取子函数 |
| 单个场景 `.tscn` | **不超过 3 层嵌套** | 子树封装成独立场景 |

> 💡 超过 **500 行**的文件必须使用 `# ── 区域名 ──` 风格的注释分隔不同功能区域，保证可读性。

当前项目最大文件 `main.gd` 为 807 行（窗口管理 + 幽灵墙 + 三模式），`pet.gd` 为 258 行。

## 2. 何时拆分，怎么拆

### 🔴 信号: 该拆分了

- 一个 `.gd` 文件里有 **3 个以上不相关的功能**
- 函数名出现 `_and_` （如 `update_position_and_draw`）
- 需要频繁滚动才能找到想改的代码
- `if/elif` 链超过 5 层

### ✅ 拆分策略

#### 策略 1: 按职责拆到独立脚本

```
pet.gd (184行)  → 拆成:
├── pet.gd           (~80行)  ← 只管状态机和输入路由
├── pet_visuals.gd   (~80行)  ← 只管 _draw() 和动画
└── pet_physics.gd   (~40行)  ← 只管物理参数设置
```

**怎么做**: 创建新脚本，用信号或直接引用连接：
```gdscript
# pet.gd 中
@onready var visuals = $PetVisuals  # 子节点上挂 pet_visuals.gd

func transition_to(state_name: String) -> void:
    # ... 状态切换逻辑 ...
    visuals.on_state_changed(state_name)  # 通知视觉层
```

#### 策略 2: 子场景封装

当 pet 要加气泡对话、表情系统、粒子特效时，不要全塞进 `pet.tscn`：

```
entities/pet/
├── pet.tscn                    ← 只有刚体+碰撞
├── speech_bubble/
│   ├── speech_bubble.tscn      ← 独立场景
│   └── speech_bubble.gd
└── particles/
    ├── heart_particles.tscn    ← 独立场景
    └── heart_particles.gd
```

在 `pet.gd` 中按需实例化：
```gdscript
var bubble_scene = preload("res://entities/pet/speech_bubble/speech_bubble.tscn")

func show_bubble(text: String):
    var bubble = bubble_scene.instantiate()
    bubble.set_text(text)
    add_child(bubble)
```

#### 策略 3: 新状态 = 新文件

要添加新行为？**永远创建新的状态文件**，不要把逻辑塞进已有状态：

```
states/
├── state.gd       ← 基类 (不要改)
├── idle.gd        ← 已有
├── walk.gd        ← 已有
├── drag.gd        ← 已有
├── fall.gd        ← 已有
├── sleep.gd       ← 新增: 睡眠状态
├── eat.gd         ← 新增: 进食状态
└── happy.gd       ← 新增: 高兴状态
```

只需要在 `pet.gd` 的 `_init_states()` 中注册新状态即可。

## 3. 通信方式选择

模块间怎么传消息？根据关系选择：

```
                    ┌──────────────────┐
                    │   EventBus       │
                    │   (全局广播)      │
                    └────────┬─────────┘
                             │ 适用于: 不知道谁在听
                             │ 例: IPC消息到达、番茄钟结束
                             │
    ┌────────────────────────┼────────────────────────┐
    │                        │                        │
    ▼                        ▼                        ▼
 信号 (Signal)          直接调用             节点组 (Group)
 父→子 / 兄弟间       父→子 (紧密关系)      "所有敌人受伤"
 例: pet → visuals    例: pet.transition_to() 例: 批量操作
```

### 选择指南

| 场景 | 推荐方式 | 示例 |
|------|---------|------|
| 宠物吃东西 → 播放音效 | **EventBus** | `EventBus.pet_ate.emit()` |
| 状态机切换状态 | **直接调用** | `pet.transition_to("eat")` |
| 父节点通知子节点 | **直接引用** | `$PetVisuals.play_animation("eat")` |
| 不知道谁需要这个信息 | **EventBus** | `EventBus.task_completed.emit(name)` |

### 🚫 禁止做的事

```gdscript
# ❌ 跨模块直接找节点 (强耦合！)
get_node("/root/Main/Pet").do_something()

# ✅ 通过 EventBus 解耦
EventBus.some_signal.emit(data)
```

## 4. Godot 特有的坑

### 🕳️ 坑 1: 物理体不要直接改 position

```gdscript
# ❌ 会导致物理引擎冲突和抖动!!
rigid_body.position = Vector2(100, 200)
rigid_body.global_position = mouse_pos

# ✅ 用力来移动
rigid_body.apply_central_force(direction * force)
rigid_body.apply_central_impulse(direction * impulse)

# ✅ 如果真的需要瞬移，先 freeze 再改
rigid_body.freeze = true
rigid_body.global_position = target
rigid_body.freeze = false
```

### 🕳️ 坑 2: `_ready()` 的执行顺序

子节点的 `_ready()` **先于** 父节点执行！

```
Main._ready()        ← 最后执行
├── Pet._ready()     ← 先执行
│   └── Collision._ready()  ← 最先执行
```

如果父节点在 `_ready()` 中设置了子节点需要的数据，子节点可能拿不到。解决方案：
```gdscript
# 方案 A: 用 await
func _ready():
    await owner.ready  # 等父节点准备好
    # 现在可以安全访问父节点数据了

# 方案 B: 用 call_deferred
func _ready():
    call_deferred("_late_init")

func _late_init():
    # 在下一帧执行，所有节点都已就绪
    pass
```

### 🕳️ 坑 3: `queue_free()` 不是立即销毁

```gdscript
node.queue_free()     # 标记为待删除，在这一帧结束时才真正删除
# 这一行 node 还活着！
print(node.name)      # 仍可访问

# 如果要检查节点是否即将被删除
if node.is_queued_for_deletion():
    pass
```

### 🕳️ 坑 4: 信号连接要注意生命周期

```gdscript
# ❌ 如果 target 被 queue_free() 了，信号会报错
source.some_signal.connect(target.on_signal)

# ✅ 安全写法: 连接前检查
if is_instance_valid(target):
    source.some_signal.connect(target.on_signal)

# ✅ 或者用 CONNECT_ONE_SHOT 只触发一次
source.some_signal.connect(target.on_signal, CONNECT_ONE_SHOT)
```

### 🕳️ 坑 5: Windows 缩放问题

Windows 的显示缩放 (125%/150%) 会导致屏幕坐标和视口坐标不一致。

```gdscript
# ❌ 用屏幕坐标创建游戏内物体
var screen = DisplayServer.screen_get_usable_rect()
wall.position.x = screen.size.x  # 可能超出视口！

# ✅ 用视口坐标
var vp = get_viewport_rect().size
wall.position.x = vp.x  # 始终正确
```

## 5. 命名规范

### 文件命名

```
snake_case.gd           ← GDScript 文件，全小写+下划线
PascalCase.tscn          ← 场景文件，帕斯卡命名 (也可 snake_case)
```

### 代码命名

```gdscript
# 类名 — PascalCase
class_name StateIdle

# 函数和变量 — snake_case
var walk_speed := 100.0
func apply_force() -> void:

# 常量 — UPPER_SNAKE_CASE
const MAX_SPEED := 500.0

# 私有函数 — 前缀下划线
func _internal_method() -> void:

# 信号 — 过去时态 snake_case
signal health_changed(new_hp: int)
signal drag_started
```

## 6. 新功能开发检查清单

每次添加新功能前，过一遍这个清单：

- [ ] 这个功能属于哪个模块？(core? entities? ui?)
- [ ] 是否需要新建文件？(大于 30 行的新逻辑 = 新文件)
- [ ] 是否需要新的状态？(→ 在 `states/` 下新建)
- [ ] 模块间通信用什么方式？(信号 / EventBus / 直接调用)
- [ ] 是否需要新的信号？(→ 在 EventBus 中声明)
- [ ] 改完后最大文件是否超过 200 行？(→ 拆分)
- [ ] 有没有直接修改 RigidBody2D.position？(→ 改用力)
